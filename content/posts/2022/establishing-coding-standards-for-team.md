许多团队、公司、组织甚至软件、框架都会面向成员和开发者提供**代码规范（Coding Standard）**，有时候它也被称为**风格指南（Style Guide）**，例如：

- Google：https://google.github.io/styleguide/
- 虚幻：https://docs.unrealengine.com/4.27/zh-CN/ProductionPipelines/DevelopmentSetup/CodingStandard/
- Vue：https://vuejs.org/style-guide/
- ……

代码规范是大规模软件开发中非常重要的一个部分。本文旨在解答，为什么建设代码规范是有必要的，以及如何建设团队的代码规范。

## 规范的意义

代码规范的核心意义通常只需要一个词就能够概括：**可维护性**。

在互联网公司的软件开发流程中，几乎所有的项目都是由团队维护、持续迭代的，这意味着：

- 代码几乎不会只由一人来维护，这会带来极高的“[巴士因子](https://zh.wikipedia.org/wiki/%E5%B7%B4%E5%A3%AB%E5%9B%A0%E5%AD%90)”
- 代码的维护时间要远远超过开发时间

因此，保证代码的可维护性对于维持一段业务的持续发展是非常必要的。代码规范的首要责任，就是保证依照规范编写的代码都能有高可维护性。

![maintainability](https://ik.imagekit.io/cyansalt/2022/establishing-coding-standards-for-team/0001-maintainability.png)

正如我的兄弟团队在代码规范中引用的名言：

> “任何一个傻瓜都可以写出计算机可以理解的代码。唯有写出人类容易理解的代码，才是优秀程序员。”
>
> -- Martin Fowler《重构》

如果你已经阅读过 [Code Review 最佳实践](/posts/best-practices-for-code-review) ，或者有过 Code Review 的实践经验，你应该会发现，如果在一场 Code Review 中出现了大量的问题/评论，通常这些问题都是细粒度的代码问题，而非设计问题。

有一个管理学理论叫“帕金森琐碎定理”，这个例子过于真实以至于我想要展开讲一下：

> 核反应工厂的财政会议要讨论三项议题：
>
> 1. 搭建价值一千万英镑的反应堆
> 2. 价值 350 英镑的员工自行车棚
> 3. 每年为合作的咖啡店赞助 21 英镑
>
> 第一个议题无论是金额还是技术含量都遥不可及，在**两分半**的讨论后就被通过了。一位成员提出了完全不同的计划，但是没有人愿意放弃目前的讨论进度所以响应寥寥；另一位熟悉项目的成员对该方案略有担忧，但他觉得解释成本过高，最终也没有说话。
>
> 第二个议题则处于大家都能理解的范围内，Softleigh 表示铝制车棚不如石棉性价比高；Holdfast 则认为应该用镀锌铁；Daring 质疑建车棚的必要性，Holdfast 对此表示反对……在经过 **45 分钟**的辩论，得出了可能节省 50 英镑的结论后，大家带着完成使命的成就感纷纷坐回原位。
>
> 也许成员们无法区分不同材质的自行车棚，但所有人都了解咖啡。第三项议题将占用**一个多小时**的时间，最终由于时间关系，在会议结束时成员们要求秘书提供更多信息，并将该议题留待下次会议讨论。

这个故事最终演化成了一个词叫做 **Bikeshedding**，意味着我们总是把讨论集中在不重要的细枝末节上，而忽视了真正重要的事情。

![bikeshedding](https://ik.imagekit.io/cyansalt/2022/establishing-coding-standards-for-team/0002-bikeshedding.png)

对于 Code Review 以及更多针对代码的交流中，我们是否把时间浪费在了缩进方式、变量命名这样的事情上，而忽略了整体设计？好的代码规范能够帮助我们提前定义前者的**最佳实践**，让我们将关注点都集中在更重要的部分上。

<br>

好的代码除了具有更好的可维护性之外，通常也会具有更好的健壮性（Robustness）。有相当一部分问题我们实际上可以通过代码规范来规避。

例如，在 JS 中你实际上可以为函数的不同参数定义相同的名称，例如：

```js
function foo(a, b, a) {
  doSomething(a);
}
```

它的实际表现是 `a` 将会引用第三个参数的值。这个特性的实际用途并不常见，更多时候更有可能的是不小心打错了参数名。如果我们有明确的代码规范甚至工具来禁止这种代码，就可以避免这类笔误造成的后果。

![robustness](https://ik.imagekit.io/cyansalt/2022/establishing-coding-standards-for-team/0003-robustness.png)

总结一下，代码规范可以帮助我们实现：

- **可维护性**
- **减少无意义的讨论**
- **避免低级错误**

## 为什么要建设规范？

看上去这个问题已经能被“规范的意义”回答了，但实际上我们要讨论的是：为什么我们要建设**属于自己团队的**代码规范？

在我所在的公司内部，我们有一份通用的前端代码规范，但很多时候，甚至是绝大多数情况下，这可能并不与你的团队、业务、技术栈适配。举几个简单的例子：

- 该规范要求 JS 文件需要使用 .js 扩展名，但由于 NodeJS 的历史原因，你很有可能需要使用 .mjs/.cjs 或者其他格式的扩展名；
- 该规范对于常量命名的要求，在你的团队内很有可能受到前端/后端/算法等合作团队的影响而打破规则；
- ……

![maintainability](https://ik.imagekit.io/cyansalt/2022/establishing-coding-standards-for-team/0001-maintainability.png)

作为团队规范，代码规范也应当适用于**既定的事实**，尽量避免为了人为制定的规范而强制改变现有的工作流程的情况出现。

<br>

从另一个角度来讲，代码规范实际上是<mark>**团队风格**</mark>的一种体现。你的团队成员可能有不同的过往经验，它们共同构成了团队独有的代码风格。在一些无关代码质量的风格问题上，拥有一套自洽的、独特的规范/代码风格，可能成为团队归属感的一部分，甚至对团队成员的生涯产生持续的影响。

<br>

团队的代码规范往往不是一次成型的，而是在不断的发展中逐步更新。在业务迭代过程中，我们也出现过一些代码规范问题导致的事故，一部分现行规范中包含着这些血与泪的教训。通过代码规范，这些事故也有效地被防止再次发生，成为代码质量保障的一部分。

<br>

总结一下，团队代码规范意味着：

- **适用性更强**
- **彰显团队风格**
- **总结历史经验**

## 原则

代码规范的建设并不是一件容易的事情。毕竟，这本质上是在统一人的思想，“罢黜百家，独尊儒术”，甚至可能影响到团队成员的利益（规范与习惯冲突 -> 开发效率降低 -> 更多工作延期 -> 绩效表现不佳 -> 升职加薪无望……）。

![standards](https://ik.imagekit.io/cyansalt/2022/establishing-coding-standards-for-team/0005-standards.png)

因此，在执行过程中，我们要格外注意一些技巧。从我所在的团队的经验出发，我为大家列举了如下内容：

### 人人有机会发声

“多数人暴政”有时不会获得一个最优的结论，但是一定能获得一个确定的结论。防止团队代码规范被团队成员质疑的最好方式是**让每个人都有表达意见的机会**。

在我所在的团队，我们的几乎所有代码规范都由团队成员投票参与决定。投票开放给所有的团队成员，但显然，你也可以选择不参与表决。

除了让所有人都有机会争取自己偏好的风格之外，这也是让团队为代码规范背书的方式。当新人加入时，不会有机会让他觉得某个制定规范的人是傻 X；相反，我们还可以用同样的形式让提出质疑的同学有机会重新发起投票。

### 逃避可耻但有用

投票总是好的，但也总是有一个问题：如果对立意见的投票结果一致怎么办？

一种方式是“*民主集中制*”：可以由负责架构的同学拍板决定最终的结果——事实上，前文提到的公司通用前端代码规范就是这样做的。这样做的好处是，你总是能够针对每个观点得出确定的结论；但是坏处是，这样得出的结论更容易被后加入的同学质疑。

所以我们常常选择另一种方式：既然不能达成有效的一致意见，那就放着不管吧！如果一个问题在团队内是争执不下的，是不是说明它本身就没有一个最佳的结论呢？也许代码规范**没有必要完全限制编码的自由**，毕竟连上海的管控区都允许居民下楼呢。

### 自动的总是优于文档

代码规范应该用什么方式呈现呢？也许一篇事无巨细的文档是完美的，但是：

![documentation](https://ik.imagekit.io/cyansalt/2022/establishing-coding-standards-for-team/0006-documentation.jpg)

因此，能够自动修复的代码，就不要只用文档描述；能够强行卡点的问题，就不要留到 Code Review 环节再处理。正因为如此，创造一个适合团队的工具也是代码规范建设的一部分。这就是为什么我把它留到最后——

## 打造合适的工具

与代码规范离不开的总是<mark>**代码优化工具**</mark>。实际上有很大一类工具都可以完成代码优化工作，包括优化编译器、格式化工具、Linter 等等。所有的这些都可以被用在你的团队项目里，用以确保代码规范能够被正确地执行。

<br>

在我所在的团队，我们使用 ESLint 和 Stylelint 完成 JS/TS/Vue 代码以及 CSS/SCSS 等样式代码的自动化检查。我们在每个项目内都将相应的工具添加为依赖，并且在多个环节运行：

- 保存文件时的编辑器检查
- 提交代码时的 Git 钩子
- MR 合并前的 CI 检查

> **下文均以前端项目为例进行介绍。**

### 通用配置

除了在每个项目内配置之外，我们还可以将这些规则整理成一份统一的依赖。

不论项目使用的框架是什么，总会有对应的工具插件可用。这些**工具插件的配置**本身就是代码规范的一部分，因此，我们只需要在项目里引用这些配置包，就可以简单地跨项目复用代码规范配置了。

### 配置预设

但，还没结束！现在，我们解决了这些插件的配置问题，但是在不同的框架下要使用哪些插件依然需要我们手动管理。因此，我们还整理了团队 Lint 规则集，用来管理不同的框架下需要执行的工具插件。这些包会自动根据当前项目的依赖关系，来分析需要应用哪些规则。

同时，幸运的是，我们依赖的这些工具都在活跃地迭代中。利用上述规则集依赖包，我们每个月都会将它们更新到最新，并检查是否有新增的特性可以应用在代码规范中。对于新增的问题，我们也可以在更新规则后对旧代码进行修复。我们甚至可以通过这种方式，将一些旧代码中的遗留问题都挖掘出来并加以修复。

### 遗留问题

对于一些较难修复的遗留代码，我们也可以在项目内将这些规则临时地禁用。

ESLint 和 Stylelint 同时也都支持仅对部分文件应用某些规则，我们也可以将出现问题的旧文件单独配置在一个 JSON 文件列表中（例如，`legacy-files.json`），并对列表中的文件禁用这些规则；另一方面，我们会在 CI 环节增加额外的检查，禁止修改该列表中的文件。这意味着：

- 如果需要修改列表中的文件，则必须将其从列表中移除
- 移除后这些文件将会再次被 Linter 覆盖，则历史问题必须被修复

通过这种方式，我们可以让这些历史遗留问题**渐进性地被修复**，同时无视那些已经完全不再维护的文件。

<mark>然而，在实际经验上，我们发现这个方式对研发流程效率存在一定影响，建议尝试该方案前根据团队和项目情况进行评估。</mark>

### 自定义规则

很多时候，工具或者插件提供的校验规则依然不能完全覆盖团队的需求，此时就需要团队维护一套自定义规则集。这其中包含的大部分是我们在推动代码规范过程中发现并整理的一些问题，例如：

- 某些代码被规范认为是不合理的，但没有现有规则能够处理
- 某些代码规范存在规则覆盖，但是手动修复难度大，需要添加自动处理的规则

同时，这些规则实际上也能够被其他团队使用！也欢迎其他的前端团队使用我们的规则集。

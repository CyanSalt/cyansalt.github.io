在计算机发展的几十年内，Code Review 已经被无数大型项目证明了是软件开发中必不可少的一环。相信很多同学也能够体会到，Code Review 是一件比想象中更加重要的事情。

但是，也许在开发的过程中，你还是会因为 Code Review 的某些问题而感到头疼，比方说：

- 我不知道什么时候发起 Code Review
- 我没有时间给别人 Code Review
- 没有人给我 Code Review
- 不知道什么时候处理 Code Review 提出的问题
- 不知道如何做 Code Review
- ……

而我将会尝试为大家一一解决这些问题，可能是一些流程规范、一些工具，或者是一些小技巧，甚至是一些我所在的团队失败的经验。

## 什么是 Code Review

对于能够看到本文的读者来说，这个问题似乎简单得有些可笑。但仔细想想，可能也不是那么回事儿。你也许知道，在 Pull Request / Merge Request 环节，GitHub 和 GitLab 都会提供 Code Review 的操作界面；那么，除此之外呢？

我认为，所有试图找出潜在问题的代码阅读都可以算作是 Code Review。例如：

- 你现在需要修复一个线上的 Bug，因此阅读一段代码，这其实也是 Code Review；
- 或者，你带的一位新同学开发过程中遇到一个问题，你和他结对编程排查，在这个过程中阅读代码也属于 Code Review

为什么要聊这个呢？其实，只要能实现 Code Review 的目的，形式并不重要。你当然可以读完同事的代码然后当面 battle 一顿，但在 MR 环节直接 Skip Code Review；或者你也可以选择在 MR 级别的 Code Review 之外组织其他形式的代码阅读。重点是：**你是不是真的能够发现代码中的问题**。

## Code Review 的意义

然而，Code Review 的意义真的仅仅在于发现代码中的问题吗？事实上，Code Review 不仅是软件开发的必要环节，同时也是**团队协作的重要组成部分**。

### 对于 Reviewee

对于新同学来说，被 Code Review 是快速熟悉团队代码规范、研发流程的直接方式；比起繁琐的文档，Code Review 更能直接体验到个人标准和团队标准的差异所在。还记得一位同学刚加入我所在的团队时，第一个 MR 就被提了 100+ 修改点；也许大家看来会有些严苛，但这切实有效地帮助他未来产出的代码达到了要求。

而对于已经加入一段时间的团队成员来说，Code Review 也是一个很好的信息同步过程。有一个专门的术语形容这个词，叫做“[巴士因子](https://zh.wikipedia.org/wiki/%E5%B7%B4%E5%A3%AB%E5%9B%A0%E5%AD%90)”：大意是，_你的团队里面是否存在这样一个人，如果他被巴士撞了（或者是因为结婚、生孩子等原因不在团队了），他所负责的工作就进行不下去了？_ 在这一点上，不论是对 Reviewee 还是 Reviewer，Code Review 就像是一场针对代码的 1on1：双方都可以互相交换观点和信息，确保这段代码，以及其他相关功能的细节被两个或更多人所知。

### 对于 Reviewer

Code Review 不是单向输出，有时甚至对于 Reviewer 有更重要的意义。

作为 Reviewer，你有机会第一时间了解到与你相关的模块有哪些改动，也有机会思考它们会对你的工作造成怎样的影响。如果你是一个模块的负责人或者是设计者，并且这个模块由多人开发维护，那你一定更能够对此表示认同。就像尤雨溪一定会参与和了解 vue-router、vuex 这些库核心代码的 Review 和讨论，因为这有助于他思考 Vue 的设计是否合理、以及缺少哪些功能。

或者相反，编写代码的人是一个大佬，那么 Code Review 也将是一个很好的学习机会：为什么这里要这样设计？这个语句的作用是什么？这不仅有助于你学习相关的技术，也可以间接推动文档或者注释的完善。

<br>

有一句格言，我想在这里也适用：人是目的，而不是手段。我们提倡 Code Review，绝不仅仅是为了提升代码质量，反而更重要的是，**让每个团队成员都能掌握更多知识，不管是技术还是业务的**。

## 如何 Code Review

Code Review 是一件看起来简单，但或许也没那么简单的事情。下面仅以日常的 MR Code Review 为例来讨论一些 Code Review 的技巧。

在阅读这篇文章的你，平时是以怎样的粒度做 Code Review 的呢？

- 仔细检查每一行代码，就像自己将这些代码重新写一遍一样，查看哪些部分与自己想象中不那么一样；
- 按照功能的粒度读懂代码意图，确认每一个功能的实现是否正确，就像在脑海中构造单元测试一样
- 大体上扫描一下代码的结构，确保没有糟糕的设计影响整体工程，就像在参与一场技术评审一样

其实，不管哪一种都是可行的，至少在我们过去的经验上如此。因为整体设计和细节常常是不可兼得的，强烈建议大家**从自己的视角出发来读代码，用自己最熟悉的方式**，通常能够起到更好的 Review 作用，以及获得更多收获。

### 审阅

不论是整体设计还是细节，你通常都可以从这些角度检查对应的修改：

- **兼容性**
  - 它通常不应该意外影响目前已有的功能，例如是否错误修改了一个可能被其他地方使用的公共模块；
  - 它应该尽可能复用一个已有的高度相似的模块；
- **健壮性**
  - 它应当支持各种可能发生的边界情况，例如 `undefined` 的出现，但也不宜过度
  - 它应当有合适的异常处理
  - （如果有）它应当按照预期添加了单元测试
- **可持续性**
  - 它应该具有良好的可读性，包括代码、注释和文档；
  - 它应该能够良好支持后续可能的扩展，比如被未来其他相似功能复用，或者是增加更多的功能；
  - 它不应该被过度设计，这可能导致未来的复杂度不降反升

这三个方面实际上对应着你的代码对过去、现在、未来的功能都能够良好支持。

其他的方面则完全是可选的，取决于你的团队是否具有这些要求：

- 这个修改是否是单一功能的？
- 你的修改是否符合特定的代码风格？
- ……

当然，最重要的原则只有一个：**这些代码是否以公认合理的方式实现了需求？**

### 评论

除此之外，如何有效地进行代码评论，也是 Code Review 非常重要的部分。实际上，Code Review 评论和日常沟通是类似的，并且可能更“亲密”——毕竟把代码交给其他人阅读是一件相当需要信任度的事情。所以，可以在这两个方面格外留意：

- **友善**。
  - 如果你在 GitHub 上贡献过代码，会发现开源社区一般都非常友好，Awesome! Good job! Nice idea! 可能是你最容易收获的评论。也许中国人生来就有一种内敛的特性，但如果大家看到好的代码，也不妨点个赞，或者评论一个【牛啤】之类的。团队氛围也正是这样慢慢建立起来的。
  - 就像文学批评一样，不会有评论家攻击陀思妥耶夫斯基是一个老赌棍，Code Review 也是一样，尽可能对事不对人，把主观的想法直接表露出来可能更好。比如“**这段代码**写得不清楚”其实不如“**我**没看明白这段代码的意图”，避免把问题变成攻击。
- **清晰**。Code Review 评论恰如编写代码一样：也许实现效果很容易，但让大家都能理解却不容易。
  - 就像每一个程序员都应该学会用 Markdown 编写文档，Code Review 评论也可以带上你的代码块和链接。有时候可能是一个你随手就能翻到的文档，或者是一小段伪代码，就能够帮助 Reviewee 快速理解你的意图。
  - 此外，有很多同学习惯通过评论指出问题，例如：“变量名**起得不好**”——这很大程度上是无效沟通。在指出问题的同时给出自己的解决方案，或者是思考，可能会更有效地解决问题。“**用动宾结构**命名这个函数吧”，或者是“统一给这些变量**加上 `user` 前缀**吧”，其实也能避免一些误会导致的反复修改。

以上都是站在 Reviewer 的视角上来讲述的。对于 Reviewee 来说，我想表达的只有一点，那就是始终记得，**你应当是你的代码的第一个 Reviewer**。因此，请对自己的代码负责。

## 制订流程规范

如果你的团队希望推行 Code Review 机制，那么一个合适的 Code Review 流程规范是必不可少的。就算所有人都掌握了上面所说的方法，我们依然需要在下面这些问题上达成一致：

### 我应当在什么时机发起 Code Review？

团队内应当明确发起 Code Review 的时间，如果发起得过早，可能因为 Review 之后代码的大规模变动造成无效工作；如果太晚，则可能留给 Reviewer 的时间不够，最终导致 Code Review 变成一个鸡肋的【点击 Approve】工作。

在我所在的团队，我们约定 Code Review 在开发联调完成和测试开始介入之间的时间发起，这样大规模的代码变化概率极小，同时也能保证 Review 的修改能够被有效回归。

在实际的操作中，这个过程可能会延后，主要视需求的大小。我的观点是，只要保证 Code Review 的有效性就可以，不需要拘泥于一个过于死板的规范。

<br>

多人开发的 Code Review 通常会更困难，可能会涉及多个 MR 合并成一个更大的 MR 的情况，在这个过程中也需要明确 Code Review 发生的时间。

在我所在的团队，我们约定，需要对每一个合入公共分支的 MR 进行 Code Review，因为这些修改都有可能造成对其他人的影响。

但在实际操作中，更多时候还是整体 Review 的，主要是出于开发效率的原因，多人合作很有可能需要互相影响，或者是共同构造一个最小可访问环境。对于这种情况，通常我们会安排多个同学专门 Review，配合需求开发前的技术评审，保证设计和实现都没有问题。

### Code Review 的时限是怎样的？

每一个 MR 的 Code Review 都应该有时间限制，如果太短，可能导致 Reviewer 不得不延误自己的工作；如果太长，则可能被无限制地拖延，最终影响项目正常进行。

在我所在的团队，我们按照代码行数来约定。500 行以下的 MR 需要在 1 天内完成，500 行以上则可以在 1 天后完成。如果 MR 超过 1000 行，则应该由多人专门 Review，或者是拆分成更小的，这也是为了保持 Code Review 的有效性。

### 如何处理 Code Review 评论？

不同的同学可能会采用不同的处理评论的策略，这可能会影响大家的工作方式：有些人可能看到评论就 resolve 代表【已读】，而有些同学则可能用 resolve 代表【处理中】乃至【已修复】、【已验证】。

在我所在的团队，我们约定俗成的是 resolve 由 Reviewer 来操作，表示已经验证；但同时也不做强制要求，即不要求代码合并前必须 resolve 全部讨论，以此来保持机制的灵活性。

<br>

评论的处理通常也会造成代码的修改，而有时候这些修改也可能会与需求上线产生冲突。因此，评论的处理也应该和 Code Review 一样设置时间限制。

在我所在的团队，我们会将评论的问题分为三个等级：

- P0：已经影响其他功能，可能造成 Bug 的问题。必须在需求上线前修复；
- P1：可能影响其他功能，设计不合理之处。应当在上线前修复，或者单开 issue 或其他方式跟进处理；
- P2：有待商榷的问题。关于代码复用和抽象的问题常常属于此类，一般会留待线下讨论，不与需求上线冲突。

在实际操作中分级的情况并不多，但这有助于在 Code Review 沟通中区分哪些问题是有必要立刻解决的。

### 其他的 Code Review 机会

除了 MR 之外，你的团队也可以提供更多其他的机会让大家能够 Review 非新需求产生的代码。

在我所在的团队，我们每个月都会举行一次 Code Review Assembly 。简单来说，由一位轮值的同学选出一段 500 行左右的代码，所有人在 1 小时内在同一篇文档中对代码进行评论，然后依次讨论这些评论。会后再由这位同学发起新的 MR 处理这些确定的评论，通过这种方式来定期回顾一些历史代码中存在的问题。

<br>

所有上面介绍的我们团队的经验实际上都不一定适用于大家各自的团队，还是需要根据业务和团队情况灵活变动。但是制定的思路通常都是类似的，那就是：**有据可依，保持灵活**。

## 使用 Code Review 工具

如果你认真阅读完上面的部分，也许会觉得：这太麻烦了！但毕竟我们是程序员嘛，能用电脑解决的事情绝不用人。我们可以使用各种工具来提高整个 Code Review 流程的效率：

### Linter / CI

没错，Linter 和 CI 也可以算作是 Code Review 工具的一部分！可能有很多时候我们 Code Review 都在为了一些没有必要的事情浪费时间，比如换行规则和分号；又或者是一些显而易见的代码错误，甚至是语法错误等等。Linter 和 CI 可以非常有效地帮助我们解决这些问题。

在我所在的团队，我们曾经尝试维护一份《Code Review 问题大全》文档，最终效果很差，因为通常大家都不会去专门查阅这些问题；相反，我们通过一系列工具手段来解决这些问题，实现了更好的效果。

作为参考，我们使用了一套自动化的 ESLint/Stylelint 规则（自动识别技术栈以启用对应的规则），配合我们自行研发的 ESLint/Stylelint 插件使用；为了提高效率，我们还制作了优先进行增量检查的 Lint CI。

### Codebase

许多大型公司内的研发设施也提供了很多 Code Review 相关的支持，例如在我所在的公司内部就有：

- Code Owners：可以指定对某些代码的修改必须由特定的同学 Review
- Skip & Privilege Users：可以跳过 Code Review 流程，或者限制只有某些同学才能跳过
- Insights：可以分析你的团队项目有多少 Review 是“闪电 Review”，也就是没有有效阅读就合并了的

在我所在的团队，我们没有限制 Skip 行为；相反，我其实比较鼓励大家合理跳过 Review，例如某些分支同步操作；通常只需要保留一些追责机制就能够防止 Skip 被滥用；

至于 Code Owners，更多时候还是需要坚持一个原则，就是：**避免把 Review 工作都交给同一个人**。

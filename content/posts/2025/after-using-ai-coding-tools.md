也算是一篇拖欠了比较久的文章了。为啥要写这篇呢？毕竟已经做了快一年 AI 相关的探索了，甚至从第一次把基于 LLM 的 AI Agent 用在工作和生活中已经快三年了，但是对 AI 的看法还是始终在不断变化。今年以来我是如何看待现在茫茫多的这些 AI Agent 产品的呢？也想利用这篇文章来做一个记录。

本文尝试面向“用过 AI 工具，尤其是 AI 编码和创作类工具，但是可能不太了解 AI 是如何实现的”读者，因此不可避免地冗余一些 AI 领域的基础知识，专业的读者们跳过相关段落即可。

我会以“提问”-“解释”的形式引出想聊的一些话题，你也可以选择感兴趣的问题单独阅读。

## 大语言模型能解决所有的问题吗？

这里我不会讨论 LLM 最终能否达到 AGI，这里只是想讨论，是否能够基于 LLM 实现任意领域的最佳 AI Agent。

答案当然是“不能”。

### 人类如何思考

LLM 的生成过程和人类的思维方式非常接近——混合了并行和串行的某种方式。我们在潜意识里并行处理很多输入的“因素”，而在显性的意识层面表现为线性、流式的思考过程。LLM 一定程度上模拟了这些过程：

- Transformer 架构的注意力机制允许模型同时考虑输入的多个部分
- LLM 的生成过程表现为 Token 一个接一个的输出

所以 LLM 其实也很好地模拟了人类在智慧上的一些表现——比如“思考”、“联想”、“创意”。但是，这个过程可能**适用于**很多工作，但或许不是**最优**的。

<br>

举个例子，在 LDM （一种扩散模型，例如 Stable Diffusion）诞生之后，一个商业应用场景是使用它来生成花式二维码。LDM 可以轻而易举将二维码隐藏在一幅绘画作品里，但是在这个例子里 LLM 就不见得能够处理得比 LDM 更好。

对于编码，LLM 可能是不够的。举一个负面的例子，我们在探索 Coding Agent 的过程中遇到过一个困难：**代码检索和召回**。很多主流的 Coding Agent 工具都没有利用 LLM 做代码索引，尽管在很多传统的工具上我们反而会通过这种方式处理项目（比如 ctags）。LLM 代码索引的思路很清晰：

- 通过 Embedding 模型将代码文本进行向量化
- 在后续的对话中对用户输入的内容也进行相同的操作
- 从前者构建的向量数据库中进行向量搜索

然而，LLM 对代码的索引效率远低于对文档的索引，这是因为，LLM 的向量化本质上生成的是“语义”的聚合，但我们很难使用语义来“划分”代码。例如：

- 如果以文件作为检索粒度，那么一些聚合文件（比如包含了所有接口声明的文件）天然就会包含更多语义，更容易被召回，从而使我们很难检索到那些即使是更精确的接口调用的文件；
- 如果以类/函数作为检索粒度，那么复杂实现的函数同样会出现上述问题

所以主流的思路其实是让 LLM 通过结构化查询工具自行检索代码，例如 ast-grep，而不是通过 Agent 来完成。

<br>

在编码过程中，我们大概率需要一种特殊的“思维架构”，就像 Diffusion 模型在图像处理过程中做的一样。在编码过程中我们实际上是在：

- **应用形式逻辑的规则**：众所周知 LLM 不（那么）擅长数学，因为数学需要遵循严格的形式逻辑，而不是仅仅是语言逻辑。严格意义上的编码也是一样的。
- **管理状态机**：追踪变量的值、程序的状态、控制条件等
- **同时处理多个抽象层次**：从应用架构，到算法，再到程序语言的语法

想象有一种结合符号推理系统的 Transformer 架构的变体，或者是从底层就更贴合代码结构的某种神经网络，基于此之上产生的大模型应该会比 LLM 更擅长代码的编写。当然，可能代价就是它在通用能力上表现得必然不如 LLM 模型。不过 Transformer 的潜力还是很强的，Suno 的 Bark 模型已经验证了在强一致性的任务上 Transformer 可以表现得比想象中还要好。

![programming-vs-coding](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0003-programming-vs-coding.png)

所以尽管 LLM 能够以惊人的还原度复现人类的智能，甚至接近 AGI，但在一些特定的领域应该存在比 LLM 上限更高的模型。理想中的 AI Agent 大概率<mark>**需要使用不同的“思维模式”来构建**</mark>。

### 如何彻底避免 AI 幻觉

幻觉问题是 AI Coding 被诟病最多的问题没有之一，尤其体现在一些“非公共知识”上，通俗来讲叫作“想当然”。对人类而言，拥有更多的经验反而会导致出现与“幻觉”相似的现象。有一个心理学名词叫作[错误记忆](https://zh.wikipedia.org/wiki/%E9%8C%AF%E8%AA%A4%E8%A8%98%E6%86%B6)，互联网时尚单品“曼德拉效应”就属于这一类。

![ai-hallucinating](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0004-ai-hallucinating.png)

幻觉的成因是之前 LLM 的重点研究方向之一，大概可以从几个角度理解这个现象：

- LLM 的**训练数据**来自于互联网，但是这些信息并不都是可靠的，尤其是中文互联网，你懂的；
- **Transformer 的本质**是在“预测”即将出现的内容，从原理上就无法保证准确性。举个例子，让一个规模有限的语言模型回答下面的问题：

    > 查理一世的继任是查理二世，查理二世的继任是 ________

    他大概率会给出“查理三世”而不是“詹姆斯七世”，因为这在语义上最完整。

- **自然语言本身**就是不严谨的。20 世纪的数学家们早就发现，我们的逻辑核心——自然数，无法存在于一个完备的系统里，更何况语言本身在不完备之外还是模糊的、充满歧义的。这些都会导致 LLM 在上下文不足的情况下从“推理”转向“推测”。

总的来说，幻觉来自于 LLM 生成的**不确定性**。对幻觉问题，工程上一般的做法要么是引入多模型交叉验证，就像本小节的第一张图一样（）；要么是提供自我评估的提示词，或是在训练阶段优化。比如要求模型思考“是否足够了解这个主题”。

不过如果实际试试就能发现，**单纯的工程手段是没法办法解决幻觉问题的**。交叉验证本身有漏网之鱼，提示词也会有注意力忽略问题。那么，如果现在模型的上下文长度是无限的，我们把所有“正确的知识”都输入给模型，有没有可能消除幻觉呢？

一个比较反直觉的事情是，模型并不是因为知道的太少才出现幻觉的，相反，大量标准化的知识加重了幻觉现象。以 D2C 为例，市面上大部分组件库的 Button 按钮组件提供了 `type=info` 属性来展示一个蓝色的按钮，如果我们的组件库通过 `variant=info` 声明蓝色按钮，那模型，甚至是开发者就有可能用错，并且越是有经验的开发者就越有可能出现这个错误。

<br>

从某种角度而言，<mark>**“幻觉”不是 bug，而是一个 feature**</mark>。“创造性思维”何尝不是幻觉的一种？“思考”本身就包含了假设-求证的过程。现在的 LLM 会通过 CoT 等方式约束“求”，通过 RAG、联网搜索来增强“证”，而“假设”部分则是生成式模型的灵魂。

LLM 的创造性与幻觉是同一个能力的一体两面，所以比起尝试消除幻觉，更好的方式是“**遵循幻觉**”。还是以上面的组件库为例，如果我们的组件库也使用 `type=info`，模型就更有可能使用正确。在实践中，我们依照约定俗称的代码架构对前端项目进行工程化调整，效果相当不错，能够让模型正确处理的编码 case 从 70% 提升到 90% 左右。

### 创造一个专业代码创作模型有没有搞头？

影响 AI Agent 可靠性的另一个因素是 LLM 的注意力问题。

- 一方面，模型的上下文有限，我们提供的任意信息都会影响模型的生成结果，甚至是提示词的措辞（在我们针对项目的提示词实验中，去除提示词中无关紧要的状语和定语，能够轻微提升生成结果的可靠性）
- 此外，由于模型的训练数据包含各类语料，LLM 可能会关注输入的特定语义，从而影响对核心语义的判断。例如，“创建脚本”可能是指达人营销中的业务场景，但 LLM 可能将其理解为“编写一个解释型的可执行文件”。

SFT 是一种常见的优化模型表现的手段，在特定领域的数据集上从基座模型预训练一个“新”模型。那么，有没有可能直接使用特定领域的数据集，通过与大模型训练的相似算法，创建一个专精于某种程序语言+业务的**小模型**呢？

![small-language-model](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0005-small-language-model.png)

回答这个问题，需要理解为什么大语言模型获得了成功。大语言模型不是简单的不同领域能力的累加，广泛的知识基础在 LLM 身上体现了 1+1>>>2 的效果。AI 领域的基本原理<mark>**规模化法则（Scaling Law）**</mark>显示了模型的参数量和、训练数据规模、训练的计算量同样能够决定模型的实际表现，这其中很多能力并不是直接训练的结果，微观层面，这表现为模型的“涌现”（emergent）和“顿悟”（grokking）。

这与人类学习的过程是相似的，小孩子不是天生就理解符号逻辑，但是在对数字的认识中逐渐“涌现”；我们也不是一开始就明白一个框架的最佳实践，但会随着使用经验的增加开始“顿悟”一种使用技巧。

<br>

训练集包含的领域数量是否也遵循 Scaling Laws？如果我们只使用代码相关的语料进行训练，模型或许能够在编码上有更高的确定性，但是大概率也意味着模型处理用户输入的能力变低了，未必能够理解常规的提示词。随着我们对输入处理能力的完善，训练集的规模持续提升，实际上我们还是将它“污染”成了现在的 LLM。

早期基于 AI 的代码补全也使用特定领域的模型，但是基于 GPT-3 的 Copilot 一经诞生就遥遥领先于其他同类产品。一个足够强的基座模型是不可或缺的。比起一个专门用于编码的模型，尝试让通用模型“更好地”理解和编写代码，可能会更有意义。

<br>

但是反过来说，小模型有没有使用场景呢？这个问题取决于模型有多“小”。类似于 Claude Code 的 Haiku 模型，在次要任务上使用规模更小的模型能够在“时间和 Token 成本”VS“任务执行效果”之间取得一个更好的平衡，但是这样的模型通常也不会很小，几十 M 甚至几 M 参数的模型几乎总是达不到期望的效果。

不过我也相信，Agent 的工程设计一样能够决定其效果的上限。多个中小型的 LM 节点合作的效果是会比一个大规模的 LM 更有潜力的。三个臭皮匠顶个诸葛亮嘛！

## AI 的代码是“创作”还是“抄袭”？

AI Coding 目前处于一个很微妙的状态，对于非专业开发者而言，AI Coding 如同阿拉丁神灯，能将各种奇思妙想变成真实的产品；但是专业开发者则分成两拨人在全面拥抱和抵触之间争论，甚至有人一边鼓吹古法编程手艺一边在写代码的时候习惯性停下来等 AI 自动补全。一个很有争议的问题是：AI 真的“会”写代码吗？AI 是在搬运它见过的代码，还是真的在按照理解实现需求？

![uses-ai-to-code](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0006-uses-ai-to-code.png)

### 抄袭？谁又不是呢？

审慎地思考一下人类的编码过程，对这个问题会产生一种更加悲观的答案：实际上我们几乎没有“原创”过代码：

- 现代前端开发流程使用各种高度封装的框架，本身就是利用框架给出的 DSL “描述”应用，框架的文档的示例代码怎么写，我们就跟着怎么写
- 底层算法已经被高度理论化，几乎所有的工具函数都是已有算法思路的整合。如果实现一个 sort，终归逃不出“少量插入，大量快排”的模式

就像在音乐领域的经典论调“好听的旋律早已经被写完了”，新的音乐大部分来自于固定的风格框架中填入重复的旋律片段，编码也是一样的，几乎所有的软件都是在“复用”已有的代码。

![songs](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0007-songs.png)

但是，“抄写”代码片段的能力，和大规模工程能力之间仍有距离，这个距离正是由前文“人类如何思考”部分提到的“编码过程思维”决定的。目前，AI 在大规模工程上缺乏可靠性，主要是因为 LLM 在通用编码能力上的“涌现”要远超工程能力，换句话说，AI 更擅长“编码”而非“编程”。

LLM 的编码能力来自于大量编码内容的训练和涌现，但是我们在工程能力上给 LLM 的输入是远远不足的，这主要归咎于我们过去没有很好地<mark>**把“工程能力”本身抽象为自然语言**</mark>的语料。传统的软件工程理论与实际开发之间必然有出入，为了让 AI 在特定工程中发挥优势，我们必须想办法实现：

- 将工程架构以自然语言的形式输入给 LLM，类似于 Deepwiki 做的事情一样
- 在微调等阶段实现对工程的“领悟”

同时，这要求 LLM 在训练阶段就接受足够多的类似的工程架构内容。目前这可能是不太容易实现的，但随着开源项目越来越多地进行上述操作，这部分成熟的语料积累起来也许就能够让 LLM 的工程能力再次提升。

（多说一句，试图用认为定义的规则，例如让 AI 更加保守地复用代码、避免修改已有代码等，在训练阶段约束 LLM 大概率是行不通的，这和“创造一个专业代码创作模型有没有搞头？”中描述的问题类似，如果没有系统性的知识，在这里避免犯错的结果就是在其他地方跌倒）

### 现在谁在创作？之后谁来创作？

从另一个角度来看，是不是所有的编码过程都是在“抄袭”呢？显然不是。如果没有 AngularJS 和 Backbone 的灵机一动，现代的 React/Vue 等框架不会凭空出现。这些灵机一动就是我想表达的代码“创作”。

<br>

尽管“创作”能力本身也是从大量的工程经验中“涌现”出来的，但至少到目前为止，**AI 编码的产物中几乎没有“创作”的成分**。目前阶段 AI 编码的产物就像是“预制菜”，它不会很难吃，但是没有人希望自己在美食上的终极目标就是预制菜。我们需要的不止是“下限”，还需要“上限”。这个上限应该由谁来给出？

创造力、抽象思维、更大规模的上下文理解能力，至少目前还是人类特有的优势。“谁来创作”这个问题，实际上是一个更深刻问题的投射，即**人与 AI 未来会如何共存**。这取决于你是降临派、幸存派还是拯救派：

- 你是否认为 AI 本质上只是人类的辅助
- 你是否认为人能够与 AI 和谐共存
- 你是否认为人的历史使命已经变成了为 AI 完成训练指导

这些都会影响你对这个问题的答案。对我来说，还是相信：

> 没有人的文明，毫无意义。

## AI 编码会让程序员失业吗？

以算法和流量为主导的现代互联网产业实际上是一个焦虑自动生产机器，所以对 AI Coding 的讨论除了它有多亮眼，第二多的就是“AI 能否代替我的工作”。2025 年我们甚至已经开始见证 AI 工作者开始取代人类的工作，AI 广告大行其道，文案、剪辑……它们似乎无所不能。那我们呢？

### 保姆的简历：熟练使用洗衣机

在软件开发这件事情上，我对 AI 的能力依然持保守态度。现在的 AI <mark>**尚不具备代替开发者的条件**</mark>，所以面对一个工具，我更愿意采用一种开放的态度，就像是对 GitHub Copilot 补全功能一样。

<br>

和过去最优秀的一批工具一样，AI Coding 必然会改变编程习惯。高性能 CPU 促生了静态检查工具，间接推进了 Rust 等语言的诞生；反过来 Rust 也推动了静态检查工具的发展，诞生了 Ruff 和 Oxc 等项目。到现在静态检查已经是工业级程序语言的标配了，越来越多的团队将对相关工具的使用视为程序员必备的能力。

<br>

如果一样工具足够好用，那么对工具的使用将成为我们必备的能力。被取代的不是所有程序员，而是那些不会使用 AI 的程序员。

![ai-will-replace-us](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0008-ai-will-replace-us.png)

### 哪些工作不再需要我们

既然 AI 能够在大部分非创造性的工作上表现良好，是不是意味着这些工作真的不再需要人的参与了？

<br>

是，也不是。这样的愿景，AI 终将实现，但这需要时间。我们能够看到现在的 AI Coding 存在很多问题，比如幻觉、工程能力等。还有一个制约 AI 编码表现的关键因素是“上下文长度”。目前主流的 LLM 上下文不超过 256K token，通常他们只能记住数十个文件，因此在一个相当庞大的需求里，AI 很容易迷失自我。

<br>

但是于此同时，这反而意味着 <mark>**AI 在处理局部问题上能够更加集中**</mark>，这就是 AI 的优势所在。例如测试用例和 API 文档的生成，这些不需要庞大工程作为输入的任务，AI 绝对是目前最好的工具。再比如代码重构、性能优化等局部性任务，AI 也能够表现出非常出色的能力。

<br>

在正确的场景使用正确的工具，这样的工作或许总是需要人来定义的。我们已经见识了目前的主流 AI 开发流程，不是端到端的 Vibe Coding，而是：人类开发者定义问题和目标，AI 负责具体的实现细节，然后人类开发者进行验证和优化。

### 新时代的保姆要做什么

如果说，几乎所有的局部任务都能被 AI 完成，那开发者需要做些什么呢？

<br>

在“如何彻底避免 AI 幻觉”部分我提到了“遵循幻觉”这个例子。从架构设计的角度看，未来注重 DX（Developer eXperience）的方向会趋向于 AIX（AI eXperience）。随着 AI 工具的普及，架构领域会出现部分公共知识的形成，这些知识会成为未来 AI 工程能力的基础。所以工程架构需要做的，就是尽可能**让自己的项目符合公共知识的描述**。

这有点像我们目前在交互设计领域看到的一样，交互的一致性重要吗？当然重要；效率呢？也很重要；但是最重要的其实是“易于理解”，或者说“符合直觉”。好的交互就是没有交互，同样的道理，好的架构就是没有架构。如果一个巨型项目不需要给 AI 输入任何额外的与架构相关的提示词，证明它做到了“易上手”“低开发成本”，这也许是未来我们进行架构设计的核心目标。

## 大家都在卷 AI，最终留下的是什么

2025 年，各种基于 AI 的工具如同雨后竹林拉屎扎屁股的春笋一样不断诞生，每个 App 都要做一个聊天框，让你在那个产品经理们想象中的业务场景里对话。其实这个东西从来没有变过，最开始是微博、电商，然后是短视频、直播、网贷，现在是短剧、AI，互联网应用的本质就是浪费你的时间。

所以我们都能预见到，再过几年，现在的这些 AI Agent 有 90% 都会消失。所以留下来的 10% 会是谁呢？

### 创造 AI Agent 有多简单

实现一个 AI Agent 其实并不复杂，因为 AI 本身就像是一个 API，你传递参数给它，它返回结果给你。现在的 AI 供应商甚至已经把 API 能力高度面向应用封装了，如果只是以“能用”为目标，实现一个 AI Agent 应该用不上半个小时就能完成。

但是简单的背后实际上意味着大家都在做一样的事情，想要做一个好的 AI Agent 并不容易。 AI Agent 的长期价值并不在它有多“智能”，这是 LLM 需要关注的事情；<mark>**AI Agent 最有长期价值的是技术产品**</mark>，包括交互界面和系统集成，这些恰恰和前端领域关系比较大。

比如我们看到千篇一律的对话交互，本质上就是用马车的思维设计火箭。看看今年的 App Store Awards 年度 App [CapWords](https://apps.apple.com/cn/app/capwords-ai-%E6%8B%8D%E7%85%A7%E8%AF%86%E8%AF%8D%E5%AD%A6%E5%A4%96%E8%AF%AD/id6738896465)，它是怎么设计这个交互，怎么把 AI 的能力无缝地融入到用户场景里的。如果抛开背单词这个场景没那么大众，可以说是一个相当高分的答卷。

![capwords](https://ik.imagekit.io/cyansalt/2025/after-using-ai-coding-tools/0009-capwords.png)

有人可能会反驳说，AI Agent 本身也是需要为效果负责的，所以 Workflow 的设计才是最核心的能力。我认同前半句的观点，但我相信 Workflow 并没有想象中那么重要。

我们在 2023 年开始的早期曾经强调提示词对 LLM 的影响，但是随着模型能力的提升，也能发现，现在大部分的模型已经能够脱离模板化的提示词很好地工作了。现在的 Workflow 也是一样，本质上是对模型能力的补丁，随着模型能力提升，LLM 本身就能够理解我们现在在 Workflow 中定义的工作了。

随着模型能力的提升，“能力堆砌”的重要性会降低。从目前的模型发展趋势我们也能窥见到这一点：

- 简单的提示词的效果会逐渐逼近甚至超过复杂的提示词
- 单个模型的完成度也会趋近于多个模型在无额外上下文上共同工作的完成度

不过模型的发展或许也是有上线的，Scaling Laws 或许和摩尔定律一样有失效的一天，此时 Agent 的真实能力才会得以体现。

<br>

AI Agent <mark>**真正对效果起作用的是“机制”**</mark>。还是以 Coding Agent 为例，简单的“读文件”工具应该如何设计呢？

- 如何控制 AI 对文件的读取？是将可能的文件默认加载到上下文中，还是通过工具调用？
- AI 应该以怎样的方式读取文件？是按照行片段读取，还是读取特定的符号，或者总是完整读取内容？

不同的 AI Agent 会采用不同的策略，也会最终影响效果。我的观点一向是“对齐人类”，就像我们在开发的时候不会一次阅读文件的所有内容一样，读文件也应该是有限获取、多次尝试的。Claude Code 有一个 [Explore 工具](https://code.claude.com/docs/en/sub-agents#explore-subagent)，它尝试在一个独立的上下文内使用快速模型进行分析，在我的复现里对代码检索的效果提升非常明显；像 InfCode 这样的工具研究也反映了类似的思路。这些机制才是决定 Agent 效果的关键。

### 做产品还是做教育？

产品领域有一个词叫“教育用户”，它假设用户很蠢，产品应该强制用户按照预设的最佳方式使用。这其实很傲慢，但对于 AI 而言这反而很重要，只不过我们不是要教育用户，而是要“教育产品”。AI 就像是一个老实的新员工，我们需要耐心地引导、训练，帮助它理解我们的期望。

<br>

上下文工程是一个典型的对 AI 进行教育的例子。我们在做 AI Coding 相关的优化过程中也做了很多类似的工作，例如：

- 大量的项目提示词和工具声明会导致 AI 陷入给定的模式中无法举一反三，形成“过载”的状态；因此我们需要保持提示词和工具简洁，同时具有“启发性”；
- 关键信息在提示词中的顺序会影响 AI 对它的注意程度，所以在一些给定的任务中（例如压缩消息历史，或者生成任务概述），一般需要使用“系统提示词”-“聊天内容”-“重复描述任务”的结构

上下文工程本质上是我们在**塑造 AI 的“记忆”**。面对一个高度可定制的 LLM，教育的意义一定比面对一个成熟的人类更加重要。所以在上下文工程中，通常我们也需要借鉴一些教育领域的技巧，在保证 AI 能够完成任务的基础上，最大程度发挥其“智能”。比如：

- 做出示范
- 对正确的行为给出肯定
- 做好预期管理

教育 AI 的过程也是在培训我们自己，最好的 AI 产品一定是那些最熟悉 AI 工具的人做出来的，因为他们知道 AI 能做什么，为什么能做，怎样做得更好。

### 新世界的无产者

在这一章节的开头我强调“交互先于效果”，但这似乎是一个悖论：既然 AI 领先于非 AI 产品的核心是生成效果，为什么交互又在 AI 产品中显得更加重要？这其实涉及一个被我称为“**技术平权**”的问题。

马克思经济学理论有一部分是“生产力决定生产关系”，现阶段 AI 已经很大程度上提升生产力了，尤其是创作领域，那生产力关系的改变在哪里呢？考虑一个最普遍的创作场景，在 AI 出现之前，如果一个开发者想要构建一个 App，对于这个 App 的图标，他可能有几种选择：

- 生产：自己画一个丑丑的——有时候甚至不如没有图标
- 消费：花钱雇人做一个——在 App 前景不确定的情况下成本很高
- 盗窃：在各种设计网站上抄一个——可能背负道德和法律的风险

而在有了 AI 之后，开发者只要很简单地和 ChatCPT 等工具对话，就能够产生不止一个效果不错的图标了。

**生产**的效率被率先革命，这必然使得**消费**和**盗窃**大幅降低，而后两者都意味着剥削（资本主义体系通过消费剥削劳动者；盗窃则是更传统直接的权益侵犯）。由于生产的门槛变得越来越低，由技能（生产资料）构成的垄断不复存在，每个人都可以通过劳动直接创造价值，至少在这个场合下消除了“分配导致不公平”的土壤。

<br>

在这个过程中，利益受损的其实是生产资料占有者，即原本拥有创作技能的人——AI 设计工具对应的设计师，AI Coding 对应的研发工程师；那获益的人呢？其实是每一个原本不具有这些技能的人。所以，回到我们的话题，Agent 产品最应该服务的对象正是这些人——比起在专业领域创造不确定性的提效工具，<mark>**面向普罗大众提供非专业工具**</mark>其实是更有前景的。

正因如此，交互作为降低使用门槛的核心要素会在一个产品中占据更核心的位置。普通用户对交互的好坏感知远超对最终效果的感知（这点可以从很多用户原声中感受到），拥有优秀交互的产品必然会有更大的优势。

当然，交互的问题是可复制性很强，亮眼的交互很容易被抄袭借鉴，但要在每个细微之处都做好也是很困难的。不过既然 AI 已经大幅提升开发效率了，也许我们就能更多关注这些角度，取得新的优势。

## 写在最后

AI 是一个前所未有的优秀工具，或许被称为新的工业革命有点过了，但是应该至少不亚于移动互联网对世界的影响。AI 会在越来越多的场景代替人的工作，但是记得提醒自己，**它不是人，它表达的不是你自己**。很多事情我们都做不好的话，它更做不好。

今天的 AI 可以写一封近乎完美的情书，但是，不要误以为它们释放的感情就是你想要说出口的，也不要把它寄给你牵挂的人，因为，那不是情书的意义。

如果可以，让它们为你选个字体，做一张电子贺卡吧，记得让你爱的人一眼能够看到你，而不是 AI 背后的，一个模糊人型轮廓。
